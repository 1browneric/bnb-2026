Build a Draft War Room

A live draft console that reads your league's feed, ranks the board on your own scoring, and tells you who to take next. This is the exact build, including the fifteen things that broke. Written from a Sleeper build; the Yahoo differences are called out at every step.

01What it does

One page, open next to the draft room, that answers a single question in under a second: who should I take right now?

It watches the league's draft feed, crosses off every player as they go, recalculates what's left against your own roster and your league's scoring, and puts one name at the top with the reason. Six-second refresh. No typing during the draft.

Around that: a full player pool with every projection source, a round-by-round plan that recalculates as the board changes, live rosters for all eight teams, a running pick log, and a status tab for injuries and suspensions.

02The Yahoo problem

This is the one real difference, and it is worth knowing before writing any code.

SleeperYahoo
AuthNone. Open read-onlyOAuth 2.0, three-legged
SetupNothingRegister an app, consumer key and secret, redirect URI
TokensN/AAccess token expires in 1 hour, must refresh
FormatJSONXML by default, JSON with ?format=json
ShapeFlat arraysDeeply nested, numeric string keys
Rate limit1000/minUndocumented, be conservative
Do this first, days ahead

Get OAuth working and pull one real draft-results response before building anything else. Do not discover on draft night that your token expired. Yahoo access tokens last an hour; the poller has to refresh automatically or it dies mid-draft.

Getting connected

  1. Register the app Go to developer.yahoo.com, create an app, request Fantasy Sports read permission. You get a consumer key and consumer secret. For a local script the redirect URI can be oob (out of band) which gives you a paste-in code.
  2. Use a wrapper, do not hand-roll yfpy handles the three-legged handshake and token refresh. It opens a browser, you paste the verification code once, and it caches the token. yahoo-fantasy-api is the other solid option and has a draft-results method that returns picks made so far while the draft is running, which is exactly the endpoint this needs.
  3. Find your league key Yahoo keys look like {game_key}.l.{league_id}, for example nfl.l.123456. The game key changes every season, so pull it from the API rather than hardcoding it.
  4. Pull one real response and save it Save the raw JSON to disk. Build the parser against that file, not against the live API. You will iterate on the parser twenty times and you do not want twenty live calls per iteration.
Yahoo's response shape

Yahoo nests everything in objects keyed by "0", "1", "count" and mixes lists and dicts at the same level. Write one flattening helper early and run everything through it. Trying to index it inline produces unreadable code and silent wrong answers.

03Architecture

Three pieces. The important design decision is that the page never talks to the fantasy API directly.

  Yahoo/Sleeper API
        |
        v
  poller  (runs every 5s, own process)
        |  writes feed.json atomically
        v
  local web server  (python3 -m http.server)
        |  serves the page + feed.json from the same origin
        v
  war_room.html  (fetches feed.json every 6s, re-renders in place)

Why a poller instead of fetching from the page

  • CORS. Neither Yahoo nor Sleeper sends permissive CORS headers, so browser fetch is blocked.
  • Secrets. The Yahoo token cannot go in a page anyone can view source on.
  • Blast radius. A bad API response corrupts one small file, not your ranked board.

The board and projections are baked into the HTML once, before the draft. The feed only carries who-took-whom. That separation is what keeps a bad poll from destroying the rankings.

Write feed.json atomically

Write to feed.json.tmp then os.replace(). Without it the browser eventually reads a half-written file and throws a JSON parse error mid-draft.

tmp = 'feed.json.tmp'
json.dump(out, open(tmp,'w'), separators=(',',':'))
os.replace(tmp, 'feed.json')   # atomic on POSIX

04Projections

Never use a site's published fantasy point total. Pull the raw stat lines and rescore them under your league's own settings.

A site's number assumes standard scoring. If your league gives 6 points for a passing touchdown, or full PPR, or a tight-end premium, every published total is wrong for you, and wrong by different amounts at different positions.

OFF = ['pass_yd','pass_td','pass_int','pass_2pt','rush_yd','rush_td',
       'rush_2pt','rec','rec_yd','rec_td','rec_2pt','fum_lost']

def score(stats, scoring):            # scoring = league's own settings dict
    return sum(scoring.get(k,0.0) * stats.get(k,0.0) for k in OFF)

Four sources were blended and averaged per player: the platform's own projections, FFToday, ESPN and CBS. Averaging matters more than picking a favourite. Where sources disagree wildly, the spread itself is the signal.

A real example. Two running backs, similar average. One had a 12-point spread across four sources, the other 25. The tight one was the safer pick, and knowing that changed the call. Keep the per-source columns and the spread visible, not just the average.

Kickers and defenses

Score these separately from a distance-bucketed stat line. If your league pays 5 points for a 50-plus yard field goal and 3 for anything shorter, a big-legged kicker on a stalling offense is worth real points over a volume kicker on a touchdown offense. That never shows up in a raw total.

05The VOR model

This is the part that makes the tool smarter than the draft room. Raw projected points are a trap.

In a superflex league a quarterback might project 380 and a receiver 270. The quarterback looks 110 points better. He is not, because the quarterback you can get four rounds later projects 335, and the receiver you can get four rounds later projects 208.

PlayerProjectedReplacementVOR
Quarterback383.8334.948.9
Receiver270.4208.162.3

The receiver is the better pick by 13 points, and the raw numbers say the opposite by 113. Every recommendation runs on VOR, never on projected points.

Deriving replacement level, correctly

Do not use a rule of thumb. Compute it from your league's actual starting slots:

  1. Count every starting skill slot in the league Teams times slots. Eight teams starting QB, 2RB, 2WR, TE, 2FLEX, SUPERFLEX is 72 skill slots.
  2. Fill them greedily Walk the projection board top down, assigning each player to a slot he is eligible for, until all 72 are full.
  3. Replacement is the best player left over Per position. That produced QB17, RB24, WR26, TE9 in this league. The flex resolved to zero tight ends and the superflex absorbed eight quarterbacks, which is why tight end replacement sat so high.

Recompute this for your league. The numbers move a lot with roster size and format.

Marginal value, not raw VOR

The bug that makes every quarterback look elite

Scoring a candidate on raw VOR means an empty starting slot is worth the player's whole projection. With no quarterback rostered, every quarterback scores about +400 and the tool recommends nothing else. Score the gain over a replacement-level filler instead: build the lineup with nine dummy players at replacement level, then measure how much the real candidate improves it.

FILL = [replacement_player(pos) for pos in slots]   # unique names, see trap 4

def marginal(player, roster):
    before = lineup(roster + FILL).total
    after  = lineup(roster + [player] + FILL).total
    return after - before

06What goes on screen

You have sixty seconds on the clock. Everything is built for a single glance.

The call. One name, huge, with VOR, weekly swing, the reason in one sentence, and a second line naming the best player available regardless of fit. Two numbers to compare, never a list to read.
Status strip. Five tiles: who is on the clock right now and which team, your next pick and how many picks away, your biggest roster hole, projected points per week, weekly swing. Nothing else earns a tile.
The room. Horizontal tiles for the teams picking before you, each showing their unfilled starting slots and their points per week. This is how you predict what goes next.
Player pool. Every player, sortable, filterable by position, with all source projections side by side, VOR, weekly swing, ADP, survival probability, and a drafted-by column that fills in live as picks land.
Round plan. One card per pick you own. Rounds already played show who you took. Future rounds show who is likely to be there, with the market's expected takes removed. Tap for the full tier.
Status tab. Every flagged player: injuries, suspensions, and anything that changes availability. Sorted by VOR so the ones that matter are at the top.

Survival probability

For each available player, the odds he lasts until your next pick. Rank the pool by ADP, count the picks between now and your turn, and run it through a normal CDF. A player with an 80 percent chance of surviving is one you can wait on; a 20 percent one you take now. This is the single most useful derived number on the page.

07Making it live

Two browser behaviours will bite. Both are cheap to handle and expensive to discover on draft night.

Hidden tabs get throttled to one timer per minute

Flip to the draft room and back and your board is up to sixty seconds stale, silently. Fire an extra refresh on visibilitychange and focus so returning to the tab updates instantly.

setInterval(tick, 6000);
document.addEventListener('visibilitychange', () => { if(!document.hidden) tick(); });
window.addEventListener('focus', tick);
A published page cannot reach an external API

If you host the war room anywhere with a content security policy, external fetches are blocked outright. That is why the poller writes a same-origin file. Guard the poller so the page still works as a static file:

if(!/^https?:$/.test(location.protocol)) return;   // static file, no polling

Show the feed's real state

A badge reading waiting, live · 24 picks, reconnecting or feed down. When the feed dies, keep the last good board on screen rather than blanking it. Mid-draft you need to know instantly whether you are looking at live data or a corpse.

08Draft day

  1. Start it early One command that launches the poller and the server and prints the URL. Have it running before the first pick, not at the first pick.
  2. Split screen Draft room on one side, war room on the other, both visible. Both visible means no timer throttling.
  3. Verify name matching before it matters Assert that every player on your board resolves to a name the feed can produce. One unmatched name is a player who never gets crossed off, and you will not notice until you draft someone who is already gone.
  4. Keep a revert copy Copy the working build before every draft-day change. When something breaks with four minutes to your pick, you restore, you do not debug.

09Fifteen traps

Every one of these actually happened. Most produced a confidently wrong answer rather than an error, which is what makes them dangerous.

1. Names with initials get silently dropped

A regex requiring two consecutive letters before a space discards A.J. Brown, D.J. Moore and T.J. Hockenson. One of them was a keeper candidate and was missing from three of four sources for days. Test your name parser against every punctuation style you can think of.

2. Team codes glued onto names

An HTML table parser produced "KC Kenneth Walker III" as a separate player from "Kenneth Walker." The duplicate showed as available while the real player was rostered. Strip a leading team abbreviation, but only when what remains still has two name tokens, or you will rename a player whose actual first name is KC.

3. Nicknames create duplicate players

Kenny and Kenneth Gainwell. Chig and Chigoziem Okonkwo. Josh and Joshua Palmer. All appeared twice, and a simulation drafted the same man in two rounds. Merge on surname plus position plus team, where one first name is a prefix of the other or a known nickname. Do not merge on initials: Bijan and Brian Robinson are two different Atlanta running backs.

4. Identical filler names collapse

The replacement-level dummy players were all named the same thing. The lineup builder deduped by name, so only one was ever placed, and every marginal calculation was wrong. Give them unique names.

5. Defenses never match

The feed calls it "Texans" or "HOU"; the projection source calls it "Houston Texans." A drafted defense silently stays on the board. Match defenses on team code, not name, and assert all 32 resolve.

6. Pick labels versus overall pick number

Printing round plus overall pick gives "4.30" instead of "4.06". Worse, a table sorted by parsing that label reordered the entire pick log into 1.01, 2.01, 3.01, 1.02. A format someone parses is an API: grep every consumer before changing one.

7. CSS display beats the hidden attribute

.modal{display:flex} overrides the browser's [hidden]{display:none}, so the close button did nothing and an empty overlay sat on the page from load. Add .modal[hidden]{display:none}. And test on computed style, not on the property you just set: the property was flipping correctly the whole time while the screen stayed broken.

8. Tooltips clipped by scroll containers

An absolutely positioned tooltip inside a table with overflow-x:auto gets clipped to the row height. Render one fixed-position tooltip element on the body instead.

9. The round plan shows the same player every round

Printing current best-available on every round card names the same man in rounds one through six. Two fixes: remove the players the market takes before each pick, and carry a running exclusion set so two of your own picks never headline the same player.

10. Stale local storage

A player marked drafted during testing persisted into the real draft and skewed the pick math. Keep manual overrides in a separate namespace from feed state, and rebuild feed state from scratch on every poll so a corrected feed self-heals.

11. Row clicks that mark players drafted

Far too easy to trigger by accident while scrolling on a clock. If the feed is reliable, do not build manual marking at all.

12. Injury scans miss non-injury absences

A running back landed on the commissioner exempt list the morning of the draft and was still the twelfth-best available player on the board. No injury search finds a legal suspension. Sweep suspensions, exempt lists, holdouts, trades, releases and depth-chart changes as separate searches.

13. Flagging is not deciding

Having found that player, the tool struck him out and refused to recommend him. That is the tool overriding the manager. He was still draftable and still a defensible late stash. Surface the status, never enforce it.

14. Big payloads make the page feel frozen

290 players as an array of objects was 94KB of repeated key names. Columnar encoding, a key list plus flat rows rebuilt at load, cut the payload by 57 percent. Profile before optimising: every render was under 20ms, so runtime was never the problem.

15. Blind string replacement in build scripts

The most expensive one. Patching generated code with str.replace() that matches nothing returns success and reports a fix that never happened. Assert the anchor exists before replacing, then grep the built output to confirm. One bad slice deleted two render functions and nobody noticed for an hour.

Where to start

Get OAuth working and save one real draft-results response. Then build the projection merge and the VOR board, which is where the actual edge lives and which needs no live data at all. The live feed is the last piece and the easiest.

Useful libraries

  • yfpy — handles the OAuth handshake and token refresh, broad endpoint coverage
  • yahoo-fantasy-api — has a draft-results method that returns picks made so far during a live draft
